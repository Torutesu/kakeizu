# リリース前チェックリスト

動作確認からリリースまでの手順。上から順に実施する。

---

## 1. 自動検証（コミット前・CIでも実行される）

```bash
pnpm typecheck      # 型
pnpm lint           # 静的解析
pnpm test           # 単体テスト
pnpm verify:db      # マイグレーション適用 + アクセス制御の検証
pnpm build          # 本番ビルド
pnpm e2e            # ブラウザでの実挙動
```

`pnpm verify:db` は一時的なPostgresを起動し、次を確認する。

- マイグレーションが順に適用できること
- `setup_all.sql` がマイグレーションと一致していること（**初回セットアップで使うファイルなので、古いと誤ったスキーマで構築される**）
- `setup_all.sql` を単体で適用できること
- 担当外・他事務所のデータに到達できないこと（10項目）

## 2. Supabaseプロジェクトの用意

1. Supabaseで新規プロジェクトを作成する
2. SQL Editor に `supabase/setup_all.sql` を貼り付けて実行する
3. **Authentication → Providers で Google を無効にする**
   （コードからは削除済みだが、プロバイダが有効なままだと認可エンドポイントを直接叩けば認証が成立しうる）
4. Authentication → Email でメール確認を有効にする
5. Storage に `koseki` バケットが作られていることを確認する（`setup_all.sql` が作成する）

### 最初の管理者を作る

招待制のため、通常の登録経路では誰も入れない。最初の1人だけは次の手順で作る。

1. Authentication → Users → Add user で自分のメールアドレスを登録する
2. アプリにログインし、組織作成の画面から事務所を作る
   （`is_bootstrap_phase()` により、組織が0件のときだけ作成が許可される）
3. 以後は管理者として他のメンバーを招待できる

## 3. 環境変数

`.env.example` を参照。本番で必須のもの。

| 変数 | 必須 | 未設定時の挙動 |
|---|:--:|---|
| `NEXT_PUBLIC_SUPABASE_URL` | ✅ | アプリが起動しない |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | ✅ | アプリが起動しない |
| `AI_NO_TRAINING_CONFIRMED=true` | ✅ | **解析が必ずエラーになる** |
| `GEMINI_API_KEY` 等（1つ以上） | ✅ | 解析が実行できない |
| `SUPABASE_SERVICE_ROLE_KEY` | 推奨 | 招待メールが送信されない（招待自体は成立する） |
| 2つ目のAIキー | 推奨 | 2モデル照合が無効になる |

**`SUPABASE_SERVICE_ROLE_KEY` に `NEXT_PUBLIC_` を付けないこと。** RLSを完全に迂回するキーで、付けるとブラウザに露出する。

## 4. 手動での動作確認

自動テストで確認できない部分。実際の戸籍を1件使って通す。

### 認証・権限
- [ ] 招待していないメールアドレスで登録できないこと
- [ ] 招待メールが届き、リンクからログインできること
- [ ] 作業者アカウントで、担当外の案件が一覧に出ないこと
- [ ] 作業者アカウントで、メンバー管理の画面に入れないこと

### 解析（実際の戸籍が必要）
- [ ] 戸籍のPDFをアップロードできること
- [ ] 解析が完了し、家系図が描かれること
- [ ] 本籍・筆頭者が「戸籍」パネルに出ること
- [ ] 和暦が西暦に変換され、原文も残っていること
- [ ] 複数枚を取り込んだとき、同じ人物が1人にまとまること
- [ ] 読み取り結果と原本を突き合わせ、**明らかな誤りがないか**確認する

### 解析のログ確認（サーバーログ）
- [ ] `戸籍解析トークン: ...` が出ること
- [ ] **キャッシュのヒット率が0%でないこと**（0%なら警告が出る）
- [ ] `戸籍解析の照合: ... → 不一致 N件` が出ること（2モデル照合が動いている証拠）
- [ ] **フォールバックの警告が出ていないこと**（出ていれば想定のモデルで動いていない）

### 編集・出力
- [ ] 人物・関係の追加・修正・削除ができること
- [ ] 編集が自動保存され、再読み込み後も残ること
- [ ] 矛盾のある人物に印が付き、右パネルの一覧から辿れること
- [ ] PDFを書き出し、**文字が読める大きさであること**
- [ ] Excelを書き出し、本籍列と戸籍シートが入っていること

### 2人での同時編集
- [ ] 2つのブラウザで同じ案件を開き、両方から編集する
- [ ] 後からの保存が先の変更を無断で上書きしないこと（衝突が通知されること）

## 5. 既知の制約（リリース時点）

利用者に伝えておくべきもの。

- **モデルの精度検証が未実施。** 実データでのベンチマーク（`pnpm benchmark`）は
  正解データの作成が必要なため未着手。現時点の既定モデルは暫定
- **画像の前処理が未実装。** スマートフォン撮影など低品質な画像での精度は未検証
- **Geminiのモデル解決が未確認。** `gemini-3.1-pro` が解決できない場合、
  静かに `gemini-2.5-pro` へ落ちる。上記のログ確認で判別する
- **招待の送信は管理者のみ。** 1時間10件・1事務所1日30件の上限がある
