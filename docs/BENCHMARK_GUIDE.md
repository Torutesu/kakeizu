# 戸籍解析モデル ベンチマーク実施指示書

**目的:** 手元の実データ（戸籍書類）で Gemini / Claude / GPT の解析精度を実測し、
その結果に基づいて本番の既定モデル（`ANALYSIS_PROVIDER` / `ANALYSIS_MODEL`）を決定する。

**背景:** 公開ベンチマークは英語文書・ラテン文字手書きが基準であり、
日本語の戸籍（手書き・旧字体・縦書き）での優劣は実測しないと分からない。
モデル一般の調査結果は [MODEL_RESEARCH.md](./MODEL_RESEARCH.md) を参照。

**成果物:**
1. `benchmark-results/<日時>/report.md` — モデル別の精度比較レポート
2. 既定モデルの決定と `.env`（本番環境変数）への反映
3. （判明した場合）プロンプト・スキーマの改善課題

---

## 0. 前提条件

- このリポジトリをローカルにclone済みで `pnpm install` が完了していること
- 比較したいプロバイダのAPIキーを `.env.local` に設定していること（1つ以上）:

```bash
# .env.local
GEMINI_API_KEY=...       # Gemini 3.1 Pro
ANTHROPIC_API_KEY=...    # Claude Opus 5
OPENAI_API_KEY=...       # GPT-5.2
```

> ⚠️ **必ず各社の有料API（データが学習に使用されないプラン）のキーを使うこと。**
> 無料枠のキーで実在の戸籍を送信してはならない。

- Supabaseは不要（ベンチマークはアプリを起動せず、解析エンジンを直接呼ぶ）

## 1. テストセットの準備

1. リポジトリ直下に `testdata/` ディレクトリを作成する（**gitignore済み** — コミットされないことを `git status` で必ず確認する）
2. 戸籍書類のPDF・画像（JPEG/PNG/WebP、各20MB以下）を配置する

**テストセットの構成方針（重要）:** 精度差が出るのは難しい書類なので、以下を意識して**10〜30ファイル**を目安に選ぶ:

| カテゴリ | 例 | ねらい |
|---|---|---|
| 易 | 平成以降のコンピュータ化戸籍 | ベースライン（全モデル満点想定） |
| 中 | 昭和の手書き戸籍（楷書） | 実務の中央値 |
| 難 | 明治・大正の改製原戸籍（旧字体・崩し字・汚損） | モデル差が最も出る |
| 特殊 | 養子縁組・再婚・複数戸籍連続のもの | 関係抽出の正しさ |
| 画質 | スマホ撮影・低解像度スキャン | 実運用の入力品質 |

## 2. 正解データ（期待値）の作成

正解データがあるファイルだけが精度スコア（再現率・適合率・F1等）の対象になる。
なくても実行はできる（人数・家族数・所要時間・成功率のみの比較になる）。

**作り方（推奨手順）:** アプリを使うのが最も速い。

1. アプリで案件を作り、対象ファイルを解析する
2. 解析結果を目視で校正する（人物の追加・削除、生没年・続柄の修正）
3. ヘッダーの「書き出し → JSON」でダウンロードする
4. 対象ファイルと同じ場所に `<ファイル名の拡張子抜き>.expected.json` として保存する

```
testdata/
├── meiji_abuki.pdf
├── meiji_abuki.expected.json   ← meiji_abuki.pdf の正解
├── showa_smartphone.jpg
└── showa_smartphone.expected.json
```

**正解データの品質基準:**
- 人物の氏名・生年月日は戸籍の原本と突き合わせて確定させる（正解が間違っていると全モデルのスコアが歪む）
- 判読不能な箇所は無理に埋めず `null` のままにする（`null` のフィールドは採点対象外になる）
- レイアウト位置（`position`）は採点に影響しない（含まれていてよい）

## 3. 実行

```bash
# 設定済みの全プロバイダ × 既定モデルで実行
pnpm benchmark

# 対象ディレクトリを指定
pnpm benchmark -- --dir testdata/difficult

# 候補モデルを明示指定（provider:model をカンマ区切り）
pnpm benchmark -- --candidates gemini:gemini-3.1-pro,anthropic:claude-opus-5,openai:gpt-5.2

# 同一プロバイダの新旧比較も可能
pnpm benchmark -- --candidates gemini:gemini-3.1-pro,gemini:gemini-2.5-pro
```

- 実行は逐次（ファイル×モデルごとに1リクエスト）。**30ファイル×3モデルで1〜2時間程度**を見込む
- 途中で失敗したモデルはスキップされ、レポートに失敗として記録される
- 費用目安: 1ファイルあたり数円〜十数円 × ファイル数 × モデル数（詳細単価はMODEL_RESEARCH.md）

## 4. 結果の読み方

実行後、`benchmark-results/<日時>/report.md` に以下が出力される:

**指標の定義（人物単位。氏名＋生年でマッチング）:**

| 指標 | 定義 | 何を見るか |
|---|---|---|
| 再現率 (Recall) | 正解の人物のうち抽出できた割合 | **取りこぼし**の少なさ。戸籍業務では最重要（見落とし＝相続人の欠落） |
| 適合率 (Precision) | 抽出された人物のうち正解に居た割合 | **幻覚・重複**の少なさ |
| F1 | 再現率と適合率の調和平均 | 総合値。モデル間比較の第一指標 |
| 生年一致 / 没年一致 | 一致した人物の日付の完全一致率 | 和暦→西暦変換と読み取りの精度 |
| 性別一致 / 続柄一致 | 同上 | 続柄解釈の精度 |
| 差分の内訳 | 取りこぼし・過剰抽出の氏名リスト | **どこで間違えたか**の定性確認に必ず目を通す |

`results.json` には各モデルの抽出データ全体が入っているので、個別の誤読を深掘りする際に使う。

## 5. 判定基準と反映

以下の優先順で既定モデルを決定する:

1. **再現率**（平均が最も高いモデル。差が2pt以内なら同率とみなす）
2. **生年・没年一致率**（日付の誤りは静かに混入するため重視）
3. **F1**
4. 同率なら**コストが低い方**（Gemini < GPT < Claude の順に安い）

**決定したら:**

```bash
# 本番（Vercel等）の環境変数に反映
ANALYSIS_PROVIDER=<勝者>          # 例: anthropic
ANALYSIS_MODEL=<勝者モデル>        # 省略可（プロバイダ既定を使う場合）
# 敗者のうち1つ以上のAPIキーも残す（自動フォールバックが効く）
```

**あわせて行うこと:**
- `docs/MODEL_RESEARCH.md` に実測結果の要約（日付・データ件数・勝者・主要スコア）を追記する
- レポートで目立った系統的誤り（例: 特定の年号の変換ミス、続柄の誤解釈）があれば、
  `lib/koseki-prompt.ts` のプロンプト改善Issueを起票する

## 6. 継続運用

- **モデルの新版が出たら**同じテストセットで再実行し、乗り換えを判断する（`--candidates` で新旧比較）
- テストセットと正解データは共有ドライブ等の**アクセス制限された場所**に保管し、リポジトリ・公開ストレージには置かない
- アプリ内でも個別ファイルの再解析時にモデルを選べる（ファイル一覧の再解析ボタン → モデル選択）。
  本番データでの抜き打ち確認に使い、使用モデルは `koseki_files.analysis_model` に記録される

## 7. 注意事項

- **機微情報:** testdata/ と benchmark-results/ はgitignore済みだが、`git status` での確認を習慣にすること。誤ってコミットした場合は履歴の書き換えが必要になる
- **レート制限:** 短時間に大量実行するとプロバイダ側の429が出ることがある。失敗が多発したらファイル数を分割して実行する
- **再現性:** 全プロバイダ temperature=0 で実行しているが、モデル側の更新で結果は変わり得る。レポートに日時とモデルIDが記録されるので、比較は同時期の実行同士で行う

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| 「実行できる候補がありません」 | `.env.local` にAPIキーを設定する |
| 特定モデルだけ全滅 | APIキーのプラン（モデルへのアクセス権）を確認。`--candidates provider:別モデル` で安定版を試す |
| スキーマ不一致で失敗 | `results.json` のエラーを確認し、再現するならIssue化（プロンプト/スキーマの調整対象） |
| `<name>.expected.json がFamilyTreeData形式ではありません` | アプリの「書き出し→JSON」で出力したファイルをそのまま使う |
