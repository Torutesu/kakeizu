#### G-01: 本籍が抽出できない（最優先）

現在のスキーマが持つ場所の情報は `birth.place`（出生地）と `death.place`（死亡地）のみで、
**本籍（戸籍の所在地）に相当するフィールドが存在しない。** プロンプトにも「本籍」の語が一度も出てこない。

相続実務では本籍は戸籍を追跡する起点であり、転籍の追跡にも必要な情報のため、欠落の影響は大きい。

必要な作業:
1. `lib/analysis/schema.ts` の `personSchema` に `registered_domicile`（本籍）を追加
2. `lib/koseki-prompt.ts` の `KOSEKI_RESPONSE_SCHEMA`（Gemini用）にも同じ項目を追加。**2つのスキーマは必ず一致させること**
3. プロンプト本文に本籍の抽出指示を追加
4. `utils/familyDataProcessor.ts` の `PersonData` に追加
5. 人物カード・編集ダイアログ・Excel出力に反映
6. 本籍は戸籍単位の情報で人物単位ではないため、**人物に持たせるか戸籍ファイルに持たせるかの設計判断が要る**。
   転籍で本籍が変わるため、人物に1つだけ持たせると履歴が失われる

#### G-02: 照合結果の一部が表示されない（解消済み）

`compareExtractions()` は `cross_person_missing_in_primary`（照合側だけが抽出した人物）を
`personIds: []` で返す。primary 側に対応する人物が存在しないため、付与先の人物がいないのが理由。

`buildUncertaintyMap()` は personIds を辿って印を付ける実装のため、**personIds が空の指摘は誰にも付かず、
画面のどこにも出ない。** 検出して保存されているのに、人の目に触れない状態になっている。

これは**取りこぼし**の指摘であり、2モデル照合で最も価値のある情報の一つ
（片方のモデルだけが見つけた人物＝もう片方が見落とした可能性）。ここが出ないと照合の効果が半減する。

**対応済み。** `components/IssuesPanel.tsx` を追加し、人物に紐づかない指摘も一覧に表示するようにした。
移動先の人物がいない指摘はボタンを無効化し、「家系図に該当する人物がいないため、移動できません」と明示している
（押しても反応しない不具合に見えないようにするため）。

E2E（`e2e/family-tree.spec.ts`）に回帰テストを置いた。検出できていても画面に出ないという不具合は
単体テストでは防げないため、この層でしか守れない。

#### G-03: 要確認の一覧がない（解消済み）

現状、要確認は人物カードの印でしか表現されない。数十人〜百人規模の家系図で、
**印の付いた人物を探すには全体を目で走査するしかない。** 確認箇所を絞るという機能の狙いが達成できていない。

**対応済み。** 右サイドバーの最上部に配置した。

- error（内容の矛盾）と warning（確認をおすすめする箇所）で区分し、件数をバッジ表示
- クリックで該当人物を選択し、キャンバスをその位置へ移動する
- 人物に紐づかない指摘もここに出る（G-02）
- 指摘が0件のときは「指摘がないことは正しさの証明にはなりません」を併記する。
  一覧が空であることを安全の根拠と誤解させないため

**未対応の改善余地:** 確認済みのチェックを付ける機能。
データ構造の追加が必要で、どの単位（指摘ごと／人物ごと）で持つかの設計判断が要る。

**G-08: PDFがA4 1ページ固定**

`exportTreePdf` は家系図全体をSVG→PNG化し、A4 1ページに収まるよう縮小する（`exportPdf.ts:189`）。
人物が増えるほど縮小率が上がり、**大規模な家系図では文字が読めなくなる。**

相続案件では3〜4世代・数十人になることが珍しくないため、実用上の問題になる可能性が高い。

対応案:
- 用紙サイズをA4/A3から選べるようにする
- 一定倍率を下回る場合は複数ページに分割してタイル出力する
- 人物一覧を別ページとして添える

要件定義書には「PDFとして出力できること」としか書いていないため契約上の不足ではないが、
実務で使えないと意味がないので優先して直すべき。

**Excel出力の確認** 本籍の列がない（G-01の波及）。それ以外は要件を満たす。

**G-05: 2モデル照合が実質使われない**

`ANALYSIS_ENSEMBLE=true` を設定しないと動かないが、`.env.example` に記載がなく `docs/MODEL_RESEARCH.md` にしかない。
設定を知らないまま運用が始まると、実装したのに一度も動かないまま終わる。

**G-06: 画像の前処理**

解像度の正規化、傾き補正、コントラスト調整のいずれも未実装で、アップロードされた原寸をそのまま送っている。
スマートフォン撮影の戸籍では精度への影響が大きいと見込まれる。

注意: 前処理は精度に直結するため、**コスト削減目的で先に入れてはならない。**
ベンチマークに条件として載せ、精度が落ちない範囲を実測してから決める。

**G-07: モデルの比較検証**

`pnpm benchmark` で3社を同一条件で流し、精度（適合率・再現率・F1）と実測原価を1つのレポートに出せる状態。
実データ（`testdata/`）と正解データの作成待ち。**正解データの作成が最も重い工程**だが、
一度作ればモデル変更・プロンプト変更のたびに再利用できる。

## 3. 設定と運用の穴

### G-10: `AI_NO_TRAINING_CONFIRMED` がコメントアウト

`.env.example` で `# AI_NO_TRAINING_CONFIRMED=true` とコメントアウトされている。
本番でこれが `true` でないと `checkDataPolicy()` が解析を止める（`lib/analysis/dataPolicy.ts`）。

意図した設計（未確認のまま機微情報を送らせない）だが、
**デプロイ直後に「解析が動かない」で詰まる導線**になっている。`docs/DEPLOY.md` に明示するか、
`.env.example` のコメントを強くする。

### G-11: Geminiのモデル解決が未検証

公式ドキュメント上のエンドポイントは `gemini-3.1-pro-preview` だが、既定は `gemini-3.1-pro`。
素のIDが解決しない場合、フォールバックで `gemini-3.1-pro-preview` → `gemini-2.5-pro` と落ちる
（`lib/analysis/chain.ts`、対策済み）。

ただし**落ちたことに気づくにはログを見る必要がある。** APIキーを入れて1回動かせば
`logTokenUsage` とフォールバック警告で判明する。運用開始前に必ず確認すること。

### G-12: Geminiのプロンプトキャッシュ

固定プロンプトは約3,900トークンで、Gemini 3.x系の最小4,096トークンをわずかに下回る。
`responseSchema` を含めれば超える可能性もあるが未確認。
`logTokenUsage` がヒット率0%のとき警告を出すので、実測で判定する。

精度には影響しない（課金のみ）ため優先度は低い。

### G-13: `public/` の実データ

以下が残置されている。

- `public/abukike_2025-07-29T16-42-29-687Z.json`
- `public/family-info-sep.json`

`public/` 配下は**ビルドに含まれ、URLを知っていれば誰でも取得できる。**
テストデータであり問題ないとの判断を以前いただいているが、
外販を視野に入れる段階では削除するか `.gitignore` 済みのディレクトリへ移すべき。
実在の氏名・生年月日を含む場合、URLが推測されなくても検索エンジンに拾われる可能性がある。

| 単体 | `pnpm test`（Vitest, 126件） | 純関数。レイアウト計算・矛盾検出・2モデル照合・名寄せ・数え年・プロバイダチェーン |
| E2E | `pnpm e2e`（Playwright, 11件） | ブラウザ上の実挙動。描画・選択・指摘一覧・要確認の印・ズーム・全体表示 |

**E2Eの構成:** `app/e2e-fixture/` に固定データの画面を置き、そこに対してテストする。

家系図エディタの中身はDBに依存しないため、認証とSupabaseを介さずに検証できる。
これがないとE2Eはログイン画面より先に進めず、価値のある部分を一切触れない。

**本番では二重にガードしている。**
- 画面側: `E2E_FIXTURES !== '1'` なら `notFound()`
- ミドルウェア側: 同じ環境変数が立っていなければ認証必須のパスとして扱う

**この層でしか守れないもの:** G-02 は「検出も保存もされているが画面に出ない」という不具合だった。
純関数のテストは全て通っていたため、単体テストでは永久に検出できない。
同種の不具合を防ぐため、指摘一覧のテストを重点的に置いている。

固定データには、実際の解析で起きうる状況を意図的に含めている
（元号の読み違いによる矛盾、西暦に変換できない日付、人物に紐づかない照合の指摘）。
