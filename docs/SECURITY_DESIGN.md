**対象:** 要件定義書 v1.1 の 4.8（戸籍の保管と閲覧期間）・7章・8章
**位置づけ:** 検討用の設計案。決まっていない箇所は「決めたいこと」に集約する
**作成:** 2026-09-11

## 1. 何から守るか

**守る対象**

| 対象 | 所在 |
|---|---|
| 戸籍の原本（PDF・画像） | Storage の非公開バケット `koseki` |
| 読み取った個人情報（氏名・生没年・本籍・続柄） | `tree_revisions.data`（jsonb） |
| 書き出したPDF・Excel | **利用者の手元。システムの管理外** |

**想定する脅威**

1. 事務所内で必要以上に見える（担当外の案件、退職者、必要な期間を過ぎた閲覧）
2. 認証情報の奪取（使い回しのパスワード、フィッシング）
3. リンク・ファイルの流出（署名付きURLの転送、書き出したファイルの共有）
4. 運用側からの流出（サービスロールキー、バックアップ、ログ）
5. 外部AIへの送信

**今回守らないもの（要件7章）** 保管基盤そのものの作り替え（専用サーバ、保管場所の指定、独自の暗号化基盤）。
暗号化された非公開の保管領域を使うところまでを前提とする。

## 2. 現状の防御（棚卸し）

| 層 | 現状 | 実装 |
|---|---|---|
| 登録 | 招待されたアドレス以外は登録できない。DBトリガで拒否する | `0005_invite_only.sql` |
| 認証 | メールアドレスとパスワード（Supabase Auth）。外部連携なし | `app/login/page.tsx` |
| 認可 | 画面ではなく**DBのRLSで強制**。担当外の案件には到達できない | `can_view_project` / `can_edit_project` |
| 保管 | 非公開バケット。PDFのみ・20MBまで。パスは `{案件ID}/{ファイルID}` | `0002_koseki_files.sql` |
| 取得 | **有効期限60秒の署名付きURL**のみ | `lib/db/kosekiFiles.ts` |
| Storage | オブジェクトにも同じ権限判定（パス先頭の案件IDで評価） | `storage.objects` のポリシー |
| 特権キー | サービスロールキーは**招待メールの送信のみ**。`server-only` でクライアントへの混入を防ぐ | `lib/supabase/admin.ts` |
| AIへの送信 | 学習に使われない条件を確認していなければ**解析を実行しない** | `docs/AI_DATA_POLICY.md` |
| 濫用の抑止 | 解析は10分20回、招待は1時間10件・1日30件 | `rate_limits` |

**現時点で空いている穴**

- **誰がいつ原本を開いたかの記録がない**（操作履歴は要件超過として削除した経緯がある）
- 書き出したPDF・Excelは手元に残り、システムの管理外になる
- パスワードの要件・二要素認証はSupabaseの既定のまま
- 退職者の無効化は管理者の手作業に依存する

## 3. 4.8「30日で作業者から見えなくする」の設計案

### 3.1 どこで強制するか

**画面だけの制御にはしない。**次の3層に同じ条件を置く。判定は1つの関数に集約する。

1. `koseki_files` の SELECT ポリシー（メタデータ）
2. `storage.objects` の SELECT ポリシー（**ファイルの実体はこちら。ここが本丸**）
3. 画面（見えない理由を示す）

```sql
-- 管理者は常に可。それ以外は案件の閲覧権限かつ取り込みから30日以内
create or replace function public.can_read_koseki_file(p_file_id uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from koseki_files f join projects p on p.id = f.project_id
    where f.id = p_file_id
      and public.can_view_project(f.project_id)
      and (
        public.is_org_admin(p.org_id)
        or f.created_at > now() - interval '30 days'
      )
  )
$$;
```

**Storage 側の書き換えが必要になる。** 現在のポリシーはパスの先頭（案件ID）しか見ておらず、
ファイル行を参照していないため、経過日数を判定できない。パスの2要素目（ファイルID）で
`koseki_files` と突き合わせる形に変える。

保存パスを `{事務所ID}/{案件ID}/{ファイルID}` へ変える案（詳細MTGのD-1）と**同時に実施すれば移行は1回で済む**。

### 3.2 期間の起点

| 案 | 内容 | 評価 |
|---|---|---|
| A | 取り込んだ日から30日 | 実装が単純。**推奨** |
| B | 案件の作業が完了した日から30日 | 案件に「完了」の状態と、それを記録する操作が別途必要になる |

### 3.3 何が見えなくなるか

- **原本（PDF・画像）** … 見えなくする
- **読み取った家系図のデータ** … 見え続ける（作業の成果物であり、これが消えると案件が成り立たない）
- **ファイルの存在・名前・取り込み日** … 一覧には残し、「保管期間を過ぎたため閲覧できません」と示す

一覧から消してしまうと「上げたはずの書類が無い」となり、**再アップロードを誘発する**。
再アップロードされれば期間が振り出しに戻るため、隠すより理由を示すほうが安全側になる。

### 3.4 「見えなくする」と「消す」は別

要件4.8が求めているのは前者。実体の削除は管理者の操作（案件の削除でStorageからも消える）。
一定期間での自動削除を入れるかは別途決めたい。入れる場合は定期実行の仕組みが必要になる。

### 3.5 作業者の削除権限

現状、作業者は原本を削除できる。30日後に「読めないが消せる」状態は不整合なので、
**読めない期間は削除もできない**ようにする（同じ関数で判定する）。

## 4. 残るリスクと打ち手

| # | リスク | 現状 | 打ち手 | 規模 |
|---|---|---|---|:--:|
| 1 | 誰がいつ原本を開いたか分からない | 記録なし | 閲覧・書き出しに限定した記録を持つ（範囲を絞った操作履歴の再導入） | 中 |
| 2 | 書き出したPDF・Excelの持ち出し | 管理外 | 出力者名・日時の透かし、出力の記録 | 小〜中 |
| 3 | パスワードの使い回し・弱さ | 既定のまま | 二要素認証、最低文字数の引き上げ | 中 |
| 4 | 退職者のアカウントが残る | 管理者の手作業 | 一定期間ログインのない利用者を管理者に知らせる | 小 |
| 5 | 署名付きURLの転送 | 有効期限60秒 | 追加の対策は不要と判断する | — |
| 6 | 管理者アカウントの乗っ取り | 招待の回数制限は実装済み | 管理者を最小人数に保つ運用。二要素認証（#3）が効く | — |
| 7 | バックアップ・ログからの漏れ | 未整理 | バックアップの保持範囲を確認し、ログに個人情報を出さない方針を明文化する | 小 |
| 8 | AIへの送信 | 対応済み | 学習に使わない条件の確認がなければ送信しない | — |

## 5. 決めたいこと

1. 30日の起点 — 取り込み日（案A）か、案件の作業完了日（案B）か
2. 経過後に作業者から見えなくなる範囲 — 原本のみか、一覧からも消すか
3. 作業者の削除権限を同時に閉じるか
4. 実体の自動削除を行うか。行うなら期間はどれだけか
5. 閲覧・書き出しの記録を持つか（7章で対象外とした操作履歴の再検討にあたる）
6. 二要素認証を入れるか

1〜3は 4.8 の実装に直結するため、着手前に決めたい。4〜6は運用開始までに決めればよい。
