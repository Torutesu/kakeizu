## 1. 利用範囲（要件3章・7章）

### 現状

| 事項 | 実装 |
|---|---|
| 事務所の単位 | `organizations` テーブル。利用者は `memberships`（事務所ID＋利用者ID＋ロール）で所属する |
| データの紐付け | 事務所 → 案件（`projects.org_id`）→ 家系図（`tree_revisions`）・戸籍ファイル（`koseki_files`） |
| 分離の強制 | Supabase の行レベルセキュリティ（RLS）。画面側の制御ではなく**DBが拒否する** |
| 2つ目の事務所 | 作れない。`create_organization` は「事務所が1つも無い間」または「登録開放モード」でのみ成功する（`supabase/migrations/0005_invite_only.sql`） |
| 事務所の切り替え | 未実装（要件どおり対象外） |
| 戸籍ファイルの保存先 | 非公開バケットの `{案件ID}/{ファイルID}`。閲覧は有効期限60秒の署名付きURL |

要件3章「1事務所での利用を前提としつつ、事務所単位で分離できる構造」は満たしている。

### 論点 1-1（D-1）分離の水準

「事務所単位で分離」には2つの水準がある。当社の実装は前者。

| 水準 | 内容 | 外部提供時 |
|---|---|---|
| 論理分離（現状） | 同一DB・同一バケット。事務所IDで区切り、RLSで越境を禁止 | そのまま多事務所へ拡張できる |
| 物理分離 | 事務所ごとにDB・バケットを分ける | 現在の設計から移行作業が必要 |

**推奨:** 論理分離で確定する。1事務所運用では差が出ず、外部提供時も RLS の分離で足りる。
ただし「顧客の戸籍を他社と同じDBに置かない」ことを事務所として表明したい事情があるなら、**いま**決めておきたい。

**あわせて決めたい細部:** 戸籍ファイルの保存先パスに事務所IDを含めるか。
現在は `{案件ID}/...` で、案件経由で事務所に辿る。将来バケットごと事務所で分ける場合はパスの変更が必要になるため、
先に `{事務所ID}/{案件ID}/...` にしておくか、必要になってから移行するかを選ぶ。
（推奨: 先に入れる。1事務所のうちは移行コストがほぼゼロ）

### 論点 1-2（D-2）外部提供時に追加開発となる項目

7章に「外部提供の際に追加開発となるもの」として列挙したい候補。この形で確定させたい。

- 他事務所の登録、事務所の切り替え、事務所をまたぐ権限
- 契約・請求の管理、利用量の計測
- 事務所ごとの利用状況の管理画面
- 事務所単位でのデータ書き出し・引き渡し・削除（解約時の対応）
- 事務所ごとの設定（保存期間、利用するAI、出力の様式）

### 論点 1-3 1事務所運用で、いま決めておきたい運用

- **利用者数の想定**（管理者・作業者・閲覧者の内訳）。招待は管理者が1時間10件・事務所で1日30件まで
- **解約・終了時のデータ**。現状は案件単位の削除と、JSON／Excel／PDFの書き出しがある。事務所まるごとの書き出しは未実装
- **戸籍ファイルの保存期間**。現状は削除するまで残る。案件終了後に自動で消す運用が要るか

## 2. 戸籍の読み取り（要件4.4）

### 現状

| 要件 | 実装 | 現況 |
|---|---|---|
| 和暦を西暦に換算 | AIへの指示（`lib/koseki-prompt.ts` 原則3） | 実装済み。**換算はAIが行い、機械的な検算はしていない** |
| 元の表記も保持 | 日付は `original_date`（原文）と `date`（西暦）の2つを持つ | **日付のみ。氏名は受け皿がない** |
| 読み取れない箇所は空欄 | AIへの指示（原則4・6）＋ 論理矛盾の検出 | 実装済み（指示による） |
| 同一人物を1人にまとめる | `utils/mergeFamilyData.ts` の4ルール | 実装済み |
| 判断がつかなければ別人として残す | 同上（保守的に判定） | 実装済み |

### 論点 2-1（D-3, D-4）「元の表記の保持」の範囲と、手修正したときの扱い

**ここが今回いちばん先に決めたい項目。** 現状は要件に届いていない箇所がある。

| 対象 | 原文の保持 | 画面で見えるか |
|---|---|---|
| 生年月日・没年月日 | 保持している（`original_date`） | **見えない。**Excel出力の「（原文）」列のみ |
| 婚姻日・離婚日 | 保持している | 同上 |
| 氏名（旧字体・異体字） | **保持していない。**データの受け皿がない（`lib/analysis/schema.ts`） | — |
| 本籍 | 原文のまま保持している（`registered_domicile`） | 戸籍一覧・Excelで見える |

さらに、**人物を手で編集して保存すると、日付の原文が消える**（`components/PersonEditDialog.tsx`）。
「西暦がおかしいので直す」という、原文がいちばん必要な場面で原文が失われる状態になっている。実装の不具合として修正したい。

**決めたいこと**

1. 「元の表記」に氏名を含めるか（推奨: 含める。旧字体は戸籍実務で意味を持つため）
2. 原文をどこで見せるか（推奨: 人物の編集画面に読み取り専用で常時表示。加えてPDF・Excelにも出す）
3. 手修正したときの原文（推奨: **原文は編集不可で残し、修正したのは西暦側だと分かるようにする**）
4. 原文と西暦が食い違う状態を「要確認」として出すか（推奨: 出す。現状は変換できなかった場合のみ警告している）

### 論点 2-2（D-5）和暦の換算をどこまで機械で保証するか

現状の換算はAIに委ねている。次の4点は換算を誤ったときに気づきにくい。

| 事項 | 現状 | 提案 |
|---|---|---|
| 元号の境界（明治45年＝大正元年、大正15年＝昭和元年、昭和64年＝平成元年、平成31年＝令和元年） | AI任せ | 元号・年から西暦を機械換算し、AIの結果と突き合わせて食い違いを「要確認」に出す |
| 「元年」の表記 | AI任せ | 同上 |
| **旧暦（明治5年12月2日以前）** | 新暦として換算されうる | **換算しない。**原文を残し、西暦は年のみとする（要決定） |
| 月日が不明 | `1910-01-XX` のように日をXXで表す | 月も不明な場合の表記を決める（推奨: `1910-XX-XX`） |

**推奨:** 換算そのものはAIに任せたまま、**機械換算との突き合わせを検算として追加する**。
AIを置き換えるのではなく、誤りを見つける仕掛けを足す形が費用対効果が良い。

（参考）現在ある検算: 戸籍としてありえない年（1600年より前・未来）、没年＜生年、親子の年齢差15〜65歳の外れ、
親の没年より後の実子の出生、続柄の出生順との食い違い、西暦に変換できなかった日付 — `utils/consistency.ts`

### 論点 2-3（D-6）名寄せの粒度と、手で直す手段

現在の同定ルール（`utils/mergeFamilyData.ts`）。誤って1人にまとめないことを優先している。

1. IDが一致する
2. 氏名が一致し、生年が一致する
3. 氏名が一致し、双方の生年が不明で、没年が一致する
4. 氏名が一致し、片方の生年のみ不明で、その氏名の人物が既存に1人しかいない

要件「判断がつかない場合は別人として残す」には合っている。一方で**実務上の当たりどころ**が2つある。

- **婚姻による改姓。**判定は姓と名の完全一致を条件にしているため、婚姻前（旧姓）の戸籍と婚姻後の戸籍では別人になる。
  相続の戸籍収集では頻出するため、**別人として残る件数は少なくないと見込まれる**
- **統合・分離の手段が「削除して貼り直す」しかない。**別人として残った2人を1人にまとめる操作、
  誤って統合されたものを分ける操作が画面にない

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 手動の統合・分離を画面に追加する | 実務の負荷が確実に下がる。**推奨** |
| B | 改姓を織り込んだ自動判定（名＋生年が一致し、婚姻の記載で姓の変化が説明できる場合に統合候補とする） | 効果は大きいが、誤って統合する危険がある。**候補として提示し、統合は人が押す**形なら両立する |
| C | 現状のまま | 同一人物が複数ノードに残り、家系図の正しさを人が担保することになる |

**推奨:** A を入れ、B は「統合候補」の提示に留める（自動では統合しない）。

### 論点 2-4（D-7）どの書類から読み取ったかを追えるようにするか

現状、人物・戸籍のデータに**取り込み元のファイルを指す情報がない**。
「この生年月日はどの書類の記載か」を確認するには、戸籍ファイルを1つずつ開いて探すことになる。

**推奨:** 人物と戸籍に取り込み元のファイルを持たせ、人物から原本を開けるようにする。
相続実務では記載の根拠に遡れることが効いてくるため、優先度は高いと考えている。

### 論点 2-5 精度の確認方法（要件6章にも関わる）

- 読み取り精度を測る仕組み（複数モデルでの実測）は用意済みだが、**実施していない**（実データ待ち）
- 画像の前処理（傾き・コントラストの補正）は未着手
- 現状の精度の担保は「2つのモデルで読み取って食い違いを出す」「論理矛盾を検出する」「要確認の一覧に集める」の3つ

**お願いしたいこと:** 検証用の戸籍を書類の種別ごとにご提供いただきたい（詳細は5章）。

### 論点 2-6 運用上の制限

- 解析は **1人あたり10分間に20回**まで。1件で20〜30通の戸籍を扱う場合、まとめて上げると制限に当たる可能性がある。上限を実務に合わせて調整したい
- 1ファイル20MBまで。PDF・JPEG・PNG・WebP に対応
- 原本の確認はダウンロードして開く形（画面内で並べて表示はできない）。読み取り結果と原本を並べたい場面が多いはずで、改善候補として挙げておきたい

## 3. 家系図の作成と編集（要件4.5）

### 論点 3-1（D-8）数え年の出し方

**現状**（`utils/age.ts`）

- 没年がある場合 … `享年◯（数え）` = 没年 − 生年 + 1
- 没年がない場合 … `数え◯歳` = 今年 − 生年 + 1
- 生年が不明な場合 … 表示しない
- 年だけで計算する（数え年は年単位の概念のため、月日が不明でも正しく求まる）
- 数え120歳を超える「没年なし」は要確認として警告を出す

**論点**

1. **「没年の記載がない」＝存命として扱ってよいか。**古い戸籍では没年の記載を追い切れていないことがあり、
   現状の表示だと明治生まれの方に現在基準の数え年が付く（120歳超で警告は出る）。
   推奨: 表示を分ける（例 `数え◯歳` と `没年の記載なし`）。どの表記にするかを当日決めたい
2. **基準日。**現状は「今日」。相続では**相続開始日（被相続人の死亡日）時点**の年齢が要ることがある。
   案件ごとに基準日を設定できるようにするか
3. 満年齢も併記するか（現状は数え年のみ）

### 論点 3-2（D-9）同時編集の競合

**現状**（`lib/db/trees.ts` / `hooks/useFamilyData.ts`）

- 編集は800ミリ秒ごとに自動保存される
- 家系図は案件ごとに1つのデータとして保存し、版数（version）を持つ
- 保存時に版数が一致した場合のみ書き込む。**他の人が先に保存していたら、自分の保存は行われない**
- 競合すると画面に「競合が発生しました」と出て、自動保存が止まり、「再読み込み」ボタンが出る
- 閲覧のみの利用者は保存しないため、競合の原因にならない

要件「後からの保存が先の変更を無断で上書きしないこと」は満たしている。無断の上書きは起きない。

**論点**

| 事項 | 現状 | 決めたいこと |
|---|---|---|
| 競合の単位 | 家系図まるごと。**別々の人物を編集していても競合する** | 実務でどの程度同時に触るか。1案件を2人以上で同時編集する場面があるか |
| 競合後の復帰 | 「再読み込み」で相手の内容を取り込む。**このとき自分の未保存の編集は失われる** | ここをどうするか（下記の選択肢） |
| 気づき方 | 画面上部の文字と再読み込みボタン | もっと強く見せるか |

**選択肢**

| 案 | 内容 | 規模 |
|---|---|---|
| A | 競合時の文言を明確にし（「再読み込みすると自分の変更は失われます」）、自分の変更をファイルに退避できるようにする | 小 |
| B | 同じ案件を他の人が開いていることを、開いた時点で知らせる | 中 |
| C | 案件を編集中は他の人を閲覧のみにする（占有ロック。編集を終えると解放） | 中 |
| D | 変更点どうしを突き合わせて統合する | 大 |

**推奨:** まず A。同時に編集する運用が実際にあるなら C まで。
1事務所・少人数で「1案件は1人が担当する」運用なら A で足りると考えている。

### 論点 3-3 要件に書かれていない実装

契約上の問題はないが、検収時に「これは何か」となるため、要件に1行ずつ足しておきたい。

- キーボードショートカット10種（`?` キーで一覧。検索・全体表示・元に戻す・保存・追加・編集・削除など）
- 表示設定（拡大縮小の感度など）
- 手で動かした人物の配置を保持する挙動

## 4. 対象としないこと（要件7章）

### 論点 4-1（D-10）記述と実装の食い違い

| 7章の記述 | 実装の実態 | 提案 |
|---|---|---|
| 複数事務所の運用機能 | 実装していない（一致） | 1-2の候補を追記して範囲を確定 |
| スマートフォンでの編集は対象外 | **狭い画面向けの操作パネルがあり、幅390pxでも編集できる** | 実態に合わせて記述を改める。動くものを「対象外」と書くと、動かなくなったときに揉めるため |
| （記載なし）操作履歴 | 要件超過として**削除した**（画面・記録・テーブルとも） | 下記 4-2 |

### 論点 4-2 操作履歴（監査ログ）を持たないことの確認

要件に無かったため削除した。記録自体が戸籍に関する個人情報を含みうるため、残さない判断も合理的である。
一方で、**誰がいつ戸籍を閲覧・書き出したかの記録**は、事務所の安全管理措置の説明を求められた場合に効く。
「持たない」ままでよいかを確認したい。持つ場合は、記録する範囲（閲覧まで／書き出しと削除のみ）と保存期間を決めたい。

### 論点 4-3 対象外として明記したい候補
